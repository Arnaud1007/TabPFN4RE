# ADR 0031: private diagnosis of NYC borough workbook headers

Date: 2026-09-29
Owner: project implementation
Affected requirements: US05, US07, US08, US22, US23 and US24
Protocol: `nyc-borough-header-diagnostic-v1`
Status: approved for implementation after architecture and security review; code and data gates pending

## Context and decision

The [frozen worksheet v2 run](../runs/u0-nyc-worksheet-inspection-v2-20260929T091128Z/report.md) replayed five XLSX files and found one complete but mismatching 21-cell candidate in the first 25 physical rows of each, with zero qualified boroughs. Its `header_sha256` was overwritten by later preamble rows and cannot identify that candidate. V2 counted 82,370 physical rows, but it did not establish the header position or any sale row. The v1 and v2 artifacts remain immutable.

Alternative A is to inspect the workbooks interactively in Excel. That would add a larger, less auditable application surface. Alternative B is to relax the v2 header rule based on a guessed difference. That would retroactively change the failed protocol. Choose a narrow offline diagnostic that **only** selects and privately records a likely header vector; it never qualifies the workbook, maps a sale field, or certifies a transaction.

## Fixed inputs and boundary

Use exactly the five captured workbook hashes from `official-exports-20260929T033558Z-62ad417fb39f` and the v2 package, printer-settings, relationship, content-type, XML, ACL, reparse/hard-link and same-handle integrity rules. The diagnostic is offline and does not call Excel, a printer API, a geocoder, the portal, or any network service. Scoring the first 25 rows may transiently read a sale-row price-like cell; it does not interpret it as a price, persist it except when a falsely selected candidate row is saved privately, or expose it publicly. It never calculates prices. The code must be committed and pushed before opening the pinned worksheet XML through this new diagnostic.

Score at most the first 25 physical `<row>` elements in the single selected worksheet. Apply the v2 row/cell/string limits, coordinate and monotone-row checks, defused XML settings and 180-second total cap. Resolve values by explicit A:U cell coordinates, inserting empty strings for missing coordinates; never use the first 21 encountered XML cells as if they were contiguous columns. For those first 25 rows, resolve at most A:U as bounded strings; cells beyond U are counted, with no value retained. Formula cells are flagged and their cached results are never read. A source-row label and physical ordinal may be retained for candidate location. After row 25, **consume the bounded defused worksheet XML stream to EOF**, validating structure, physical-row/coordinate caps, decoded-size limit and ZIP CRC while clearing row elements without extracting cell values. A malformed or oversized tail rejects the diagnostic rather than publishing a candidate. The scanner must not retain subsequent sale rows. The outer workbook hash before and after the same open handle remains required.

For shared-string cells in the first 25 rows, collect only their bounded integer indices during the worksheet scan. Stream the entire bounded shared-string XML through EOF with defused XML; retain text only for requested indices and clear every other string element. This may transiently parse bytes originating outside the first 25 sale rows, but it must not retain or interpret those other strings. Do not use the v2 `_shared_strings` helper, which materializes the full table.

Score each of the first 25 rows by the number of position-wise **exact** matches to the pinned 21-column API header after trimming surrounding whitespace with Python `str.strip()` only. Missing A:U coordinates contribute empty strings; preserve all 21 positions. Count nonempty cells and formula cells separately. Select a candidate only if its score is at least five and it is the **unique** highest-scoring row. A tie or lower score yields `no_unique_candidate`; a uniquely highest candidate containing a formula in A:U yields `rejected_formula_candidate`. Malformed package or XML yields `rejected_structure`. Input hash/ACL/IO/time failure makes the **whole run incomplete** with no valid aggregate. This threshold is an audit triage rule, not evidence that the candidate is the true official header. The scanner must retain the selected row's **candidate cell strings** and no other row values.

Write the selected 21 candidate cell strings, source row number, physical ordinal, exact-match score, nonempty count, beyond-21 count and exact SHA-256 fingerprint to a protected, Git-ignored private result. The fingerprint is SHA-256 of the UTF-8 encoding of the ordered, `str.strip()`-trimmed 21 strings joined by ASCII unit separator; it is calculated **once from the selected row**, so later rows cannot overwrite it. Public output may contain borough, pinned workbook hash, candidate position, score, counts, fingerprint and safe failure category. It must never contain raw cell strings, addresses, apartment identifiers, prices or sample sale rows. If no candidate is selected, retain only safe counts privately and publicly. Every public result has `scope: candidate_only`, `qualified_borough_count: 0` and `label_status: unqualified`; each file has its separate `candidate_found`, `no_unique_candidate` or `rejected_*` status. Even a strong candidate is not schema acceptance.

The output directory is a new, protected `data/raw/nyc_dof/header-diagnostic-YYYYMMDDTHHMMSSZ-12hex/` with an intent, private result, redacted public-projection result and hash manifest created exclusively. Do not overwrite an existing run. An offline replay reads the same pinned workbook bytes and compares **canonical JSON bytes** of both the recomputed private candidate vector and redacted public projection with the saved files. Run timestamps and host provenance belong only in the intent, outside recomputed equality. A failed or partial run stays incomplete and cannot be published as a valid diagnosis. Public evidence records code commit, environment lock, source hashes, exact commands, tests, replay, aggregate and limitations.

## Tests and next decision

Write RED synthetic tests before implementation: exact and slightly changed headers; unique versus tied score; score below five; a high-scoring formula row; missing A:U coordinates, duplicate/nonmonotone row and cell coordinates, and extra cells; selective shared-string retention and inline strings; DTD/entity, malformed tail and oversized decoded XML; source hash change, ACL/link substitution, no-overwrite and incomplete replay; byte-identical private/public replay; public redaction when a noncandidate row contains an address or price-like string. Require at least 80% branch-aware coverage for the new diagnostic, the full repository suite, Ruff, dependency checks and independent code/Python/security review.

The result is a **candidate header description**, not an approved schema mapping. Compare candidate vectors and the official XLSX/portal documentation in a subsequent decision. If a mapping is justified, freeze a new worksheet qualification version and rerun on the same hashes in a new directory; report v1/v2 failures alongside it. Rights, first availability, close-date semantics, transfer identity and the 200-record manual audit remain separate blockers for U0 and G-US.
